# ClickHouse HTTP interface

smolquery takes the inserts and runs the queries a ClickHouse HTTP client
sends, on its own listener, so a producer or a reader that speaks ClickHouse
over HTTP can point at smolquery instead. The `:clickhouse` role starts the
edge (`SmolqueryClickHouse`, T-477). The insert is T-476, and queries are
T-478. [clickstack.md](clickstack.md) is the recipe for pointing HyperDX at it.

```sh
curl -sS "http://127.0.0.1:8123/?query=INSERT%20INTO%20logs.events%20FORMAT%20RowBinaryWithNamesAndTypes" \
  -H "X-ClickHouse-User: default" \
  -H "X-ClickHouse-Key: $SMOLQUERY_API_KEY" \
  --data-binary @rows.bin

curl -sS "http://127.0.0.1:8123/" \
  -H "X-ClickHouse-Key: $SMOLQUERY_API_KEY" \
  --data-binary "SELECT count(*) AS n FROM logs.events FORMAT JSON"
```

## The listener

- **Port.** `8123`, ClickHouse's HTTP port (`18123` in dev). `SMOLQUERY_CLICKHOUSE_IP` and `SMOLQUERY_CLICKHOUSE_PORT` move it. It binds `127.0.0.1` by default.
- **URL length.** The statement travels in the URL, so a request line may be up to 1 MiB, ClickHouse's `http_max_uri_size`. A longer one is a bare 414. Each URL parameter holds one value; a list or a map (`database[x]=1`) is a 400 `BAD_ARGUMENTS`.
- **Plain HTTP.** The edge does not terminate TLS. Bind it beyond the node only behind a TLS terminator.
- **Password.** The API key (`SMOLQUERY_API_KEY`), or `SMOLQUERY_CLICKHOUSE_PASSWORD` when set. A node with the `:clickhouse` role and neither refuses to boot.
- **How a client sends the password.** The ways ClickHouse takes it: the `X-ClickHouse-Key` header, HTTP basic auth, or the `password` parameter. A `Bearer` token works too. When a request carries more than one, the first in that order wins. The user name is accepted as given.
- **Health checks.** `GET /` and `GET /ping` answer `Ok.` without a password, as ClickHouse does.
- **Refused before the body.** A missing or wrong password is a 401 with code 516 `AUTHENTICATION_FAILED`, on every path. An insert is then counted against the in-flight limit before its body is read, as the API's insert is. Over the limit is a 429 with code 202 and `retry-after: 1`.
- **Paths.** Everything happens on `/`. Any other path but `/ping` is a 404.
- **Metrics.** Requests are counted in `smolquery_clickhouse_requests_total`, by status class.

## The insert

`POST /?query=INSERT INTO db.table (columns) FORMAT RowBinary`. The `INSERT` is in the `query` parameter, and the body holds the rows.

- **Statement.** `INSERT INTO [TABLE] [db.]table [(column, ...)] [SETTINGS name = value, ...] FORMAT name`. Keywords are case-insensitive, and names may be backquoted or double-quoted. Nothing but whitespace and one `;` may follow the format name.
- **Table.** The dataset is the statement's qualifier, else the `database` parameter, else the `X-ClickHouse-Database` header, else `default`.
- **Formats.** `RowBinary`, `RowBinaryWithNames` and `RowBinaryWithNamesAndTypes`. A plain `RowBinary` body carries no types, so each column is read as the type its smolquery column implies: `Int64`, `Float64`, `String`, `Bool`, `DateTime64(6)` or `DateTime64(9)`, `Date32`, `Decimal(P, S)`, `Map(String, String)`, wrapped in `Nullable` when the column is nullable. A producer with other ClickHouse types, such as `UUID` or `UInt8`, must send `RowBinaryWithNamesAndTypes`.
- **Timestamps.** `DateTime` and `DateTime64(P)` go into a `TIMESTAMP` column at microseconds, dropping any digit past the sixth, or into a `TIMESTAMP_NS` column with all nine. `TIMESTAMP_NS` holds 1677-09-22 to 2262-04-11 23:47:16.854775806, and a value outside that refuses its row. The zone argument is ignored: values are UTC.
- **All or nothing.** When any row is refused, none is written, as in ClickHouse. A nonzero `input_format_allow_errors_num` or `input_format_allow_errors_ratio` writes the other rows instead, without enforcing the number.
- **Settings.** `insert_deduplication_token` is the idempotency key, as `insertId` is on the API's NDJSON insert. Every other setting is accepted and ignored. A statement's `SETTINGS` clause wins over the URL.
- **Limits.** The body and the NDJSON its rows decode to are each held to `SMOLQUERY_INSERT_MAX_NDJSON_BYTES`, the API's limit. Over it is a 413; send smaller blocks. The edge keeps its own in-flight counter, sized by `SMOLQUERY_INSERT_MAX_IN_FLIGHT_BYTES` as the API's is. A node running both the `api` and `clickhouse` roles holds two counters, each with that limit.
- **Answers.** A 200 has an empty body and an `X-ClickHouse-Summary` header. A failure answers ClickHouse's text form, `Code: N. DB::Exception: message. (NAME)`, with `X-ClickHouse-Exception-Code`: 62 `SYNTAX_ERROR`, 73 `UNKNOWN_FORMAT` on a 404, as ClickHouse answers it, 60 `UNKNOWN_TABLE`, 81 `UNKNOWN_DATABASE`, 33 `CANNOT_READ_ALL_DATA` for a body that ends mid-row, 117 `INCORRECT_DATA` for rows that cannot be written, 202 `TOO_MANY_SIMULTANEOUS_QUERIES` on a 429, 516 `AUTHENTICATION_FAILED` on a 401, and 1002 `UNKNOWN_EXCEPTION` on a 503. A retryable answer carries `retry-after`. An `INSERT` in the body alone, with no `query` parameter, is a 501 `NOT_IMPLEMENTED`.

## Queries

A query is any `POST /` whose `query` parameter is not an `INSERT`, or a `GET /?query=`. The node needs the `query` role too.

- **Statement.** The `query` parameter, then the body, joined by a newline, as ClickHouse joins them. The two together may run to 262,144 bytes, ClickHouse's `max_query_size`.
- **Dialect.** The statement runs as the API's and the Postgres wire's do, with the same planner, tiers and result cap. ClickHouse's dialect is met part of the way. Its function names are DuckDB macros, and a job defines the ones its statement names, so a statement that names none pays nothing but a scan of its text (17 µs measured; HyperDX's histogram names four, about 2 ms): the date and time family (`toStartOfInterval`, `toStartOf*`, `toDateTime`, `toDate`, `fromUnixTimestamp64Milli`, `toUnixTimestamp*`, `now64`, `parseDateTime64BestEffort`), `hasToken`, `notEmpty`, `mapContains`, `indexHint`, `has`, `match`, the `-If` aggregates, `uniq`, and the `to<Type>`, `-OrZero` and `-OrNull` casts. Syntax the engine's parser refuses is rewritten first: an alias repeated inside `GROUP BY` or `ORDER BY`; `CAST(x, 'Type')`; a parametric aggregate, `quantile(0.95)(x)` or `groupUniqArray(20)(x)`, whose parameters move behind its arguments; `LIKE` with a backslash in its pattern, which gets `ESCAPE '\'`; a bare `default.` database; `isNull`, `isNotNull` and `any`, which are the parser's own words; `WITH (expr) AS alias`, whose alias is written as its expression wherever it is read; `JSONExtract(json, 'Type')`, which becomes a cast; and `MD5(x)`, which answers bytes as ClickHouse's does. `ARRAY JOIN`, `LIMIT BY` and the rest fail as the engine reports them. [clickhouse-sql-gaps.md](clickhouse-sql-gaps.md) says what each function does differently and what is missing. `clickhouse_functions: false` on the query service switches the macros off.
- **The catalog.** `system.databases`, `system.tables`, `system.columns`, `system.settings`, `system.data_skipping_indices`, `system.table_engines` and `system.one` answer, as do `DESCRIBE [TABLE] db.t`, `SHOW DATABASES`, `SHOW TABLES [FROM db]` and `EXISTS [TABLE] db.t`. A table's `engine` is `MergeTree`, and its `sorting_key` and `primary_key` are its clustering key. A column's type is the ClickHouse type an insert reads it as, `Nullable` unless the column is not, and a materialized column's `default_type` is `MATERIALIZED`. `system.tables` has ClickHouse's `table` column beside `name`. Its `total_rows` is filled in for a statement that reads it, for the tables that statement's own `WHERE` selects (at most 32; more is a refusal, not a partial sum): the query service plans each table without running it, and the plan's sizes give the rows in both tiers, hot included. A count that cannot be had refuses the statement with `retry-after`, since a `NULL` would read as an empty table. It is `NULL` for a statement that does not read it, such as a `SELECT *`, and for any shape but one `SELECT` over `system.tables` alone; `total_bytes` is always `NULL`. A `system` table is recognised whether its name arrives bare or quoted (`"system"."tables"`), as `Identifier` parameters write it. `system.settings` and `system.data_skipping_indices` have no rows. The rows are read from smolquery's catalog at most once a second, in the edge's own engine, so the edge reads the lake's catalog as the Postgres edge does. A statement is the catalog's only when every table it reads is a `system` one; a `system` table not listed here is code 60 `UNKNOWN_TABLE`.
- **Format.** A trailing `FORMAT name` in the statement, else the `X-ClickHouse-Format` header, else the `default_format` parameter, else `TabSeparated`. Taken: `TabSeparated` (`TSV`), `TabSeparatedWithNames`, `TabSeparatedWithNamesAndTypes`, `TabSeparatedRaw`, `CSV`, `CSVWithNames`, `CSVWithNamesAndTypes`, `JSON`, `JSONCompact`, `JSONEachRow`, `JSONCompactEachRow`, `JSONCompactEachRowWithNames`, `JSONCompactEachRowWithNamesAndTypes` and `RowBinaryWithNamesAndTypes`. Another is a 404 with code 73. A result with no rows still says its columns, as ClickHouse's does: `meta` in `JSON` and `JSONCompact`, the names and types lines in the `WithNames` and `WithNamesAndTypes` formats. HyperDX's histogram reads `meta` from an empty window and fills the buckets itself (T-509).
- **Types.** Every column is `Nullable` except a map: `Int64`, `Float64`, `String`, `Bool`, `DateTime64(6)`, `Date32`, `Decimal(P, S)`, `Map(String, String)`. A list is an `Array(Nullable(T))`. A `VARIANT` column is `JSON` (T-521), in `DESCRIBE`, in `system.columns` and in a result's `meta`: in the JSON formats its value is the nested document, in the text formats its JSON text. Read a key off it as ClickHouse does, `toString(metadata.context.application)`, backticked or not, to any depth; a missing path is `NULL`. `dynamicType(path)` names what a path holds: `Int64`, `Float64`, `String`, `Bool`, `Array(Nullable(String))`, `JSON` for a nested object, `None` for nothing. A path read without `toString`, `SELECT metadata.attempts`, answers as `Dynamic` when it holds anything but an object. Numbers inside a document are written as the document had them, a 64-bit integer included, where a 64-bit integer column is quoted. `JSONDynamicPathsWithTypes(col)` answers a row's leaf paths, dotted, as a `Map(String, String)` of path to type, and `groupUniqArrayMap(m)` merges such maps into a `Map(String, Array(String))`: what HyperDX asks to list a `JSON` column's keys. It reads the documents it is given, so bound it with a `LIMIT`, as HyperDX does. `RowBinaryWithNamesAndTypes` is the exception: ClickHouse's binary `JSON` is a layout of typed paths, not text, so there the column is declared `Nullable(String)` and carries the JSON text. The same holds on insert: send a `VARIANT` column as a `String` of JSON, which is how a plain `RowBinary` body is read; a producer that takes `JSON` from `DESCRIBE` and sends ClickHouse's binary form is refused. In JSON a 64-bit integer is a quoted string, as ClickHouse writes it by default. A `NULL` map answers as the empty map, since its type is not `Nullable`. A value that is not UTF-8 has its invalid bytes replaced with U+FFFD in the JSON formats; `TabSeparated` and RowBinary carry them as they are.
- **Names and timestamps.** An unaliased `count()` or `count(*)` answers as `count()`, ClickHouse's name for the column, not the engine's `count_star()`. With `date_time_output_format=iso` a timestamp is `2026-09-19T10:11:29.500000Z` in the text formats; without it, `2026-09-19 10:11:29.500000`. A `TIMESTAMP_NS` column answers all nine of its digits, and a map answers its keys in the order they were stored: a client that sends a value back to find its row, as HyperDX does on a row click, matches it.
- **Connecting.** `version()` answers `24.8.1.1`, the ClickHouse release whose HTTP behavior the edge follows, and `timezone()` answers `UTC`. Both are rewritten in the statement's code only, never inside a string literal or a comment. So the `select 1, version()` that `ch`, the Elixir client, runs on connect succeeds.
- **Settings.** `max_execution_time`, in seconds, bounds the query; a value past what a timer takes, a client's way of saying "no limit", is held to the longest one, about 49 days. `date_time_output_format=iso` is read too. Every other setting is accepted and ignored. A setting arrives as a URL parameter or in the statement's `SETTINGS name = value, ...` clause, before or after `FORMAT`; the clause wins. A `SETTINGS` clause that ends a subquery is dropped.
- **Parameters.** `{name:Type}` placeholders are filled from the request's `param_<name>` values, each written into the statement as a literal of its type: `Identifier` as a quoted name, `String` (and `UUID`, `FixedString`, `Enum`, `IPv4`, `IPv6`) as a string read from ClickHouse's escaped form, the integer and float types as a checked number, `Bool`, `Date`, `DateTime` and `DateTime64`. `Nullable(T)` and `LowCardinality(T)` read as `T`, and `\N` is `NULL`. A placeholder with no value is code 456 `UNKNOWN_QUERY_PARAMETER`. A value its type does not take, or an `Array`, `Map` or `Tuple` parameter, is code 36 `BAD_ARGUMENTS`. One parameter may fill many placeholders.
- **Quoting.** Backquoted identifiers are read as double-quoted ones, and ClickHouse's backslash escapes in a literal or a quoted name (`'it\'s'`, `'a\tb'`, `'\x41'`) become the characters they stand for. An escape ClickHouse does not know, such as `\_`, keeps its backslash.
- **`EXPLAIN ESTIMATE`.** `EXPLAIN ESTIMATE <statement>` answers what the statement would read, without running it: ClickHouse's columns `database`, `table`, `parts`, `rows`, `marks`, in one row. The statement under it is filled, quoted and rewritten as it would be to run, then planned, and `rows` and `parts` are the rows and files the plan keeps: in the hot tier after the planner's pruning and Top-N bound, in the sealed tier every segment at the snapshot, since those are pruned inside the engine. So it is an upper bound, and a narrow search over a large sealed table estimates the whole table. They are `NULL` when the plan has no sizes to give. `database` and `table` are empty and `marks` is `0`. A statement that does not bind answers its error. HyperDX sends it before each search and reads `rows`.
- **What could not be answered.** A statement refused for a reason that is the dialect's — 62, 46, 47, 60, 73, 456 or 36 — is logged as the client sent it, with its `user-agent`, and counted in `smolquery_clickhouse_unanswered_total` by code. `SMOLQUERY_CLICKHOUSE_UNANSWERED_LOG` is `redacted` (the default: string literals become `'?'`, and the engine's error is cut to its first line), `verbatim`, or `off`, which still counts.
- **GET is read-only.** As in ClickHouse, a `GET` whose statement is not a `SELECT`, `WITH`, `SHOW`, `DESCRIBE`, `EXPLAIN` or `EXISTS` is code 164 `READONLY`.
- **Answers.** A 200 carries `X-ClickHouse-Format`, `X-ClickHouse-Query-Id` (the job id), `X-ClickHouse-Timezone` and `X-ClickHouse-Summary`, whose `read_rows` and `read_bytes` are what the plan scanned. A statement with no result, such as an `ALTER TABLE`, answers an empty body without `X-ClickHouse-Format`. A failure is 62 `SYNTAX_ERROR`, 60 `UNKNOWN_TABLE`, 46 `UNKNOWN_FUNCTION`, 47 `UNKNOWN_IDENTIFIER`, 456 `UNKNOWN_QUERY_PARAMETER`, 396 `TOO_MANY_ROWS_OR_BYTES` past the result cap, 159 `TIMEOUT_EXCEEDED`, 202 `TOO_MANY_SIMULTANEOUS_QUERIES` on a 429, or 1002 `UNKNOWN_EXCEPTION`, with a 503 and `retry-after` when the query service or a buffer node cannot be reached.
